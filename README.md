# GovFin 决策智能体

> 赛题3 · 基于华为 ModelEngine Nexent 打造**可进化决策智能体**
> 场景：金融 + 政务跨域授信决策

一句话：**把政务侧散落在登记表、影像件、判决书里的"沉睡数据"，变成金融侧一条能逐环回指原文的授信依据链。**

---

## 一、它解决什么问题

授信审批的真实困难不在于"少一个模型"，而在于**证据散了**：

- 企业的用工真实性在社保缴纳记录里，是政务数据；
- 偿债能力在财务报表里，是金融数据；
- 判不判、卡在哪条红线，在监管条款里，是规则数据；
- 而这三者之间**原本没有任何一条边相连**。

客户经理拿到的是三个孤立的事实，最后只能拍脑袋。GovFin 做的事是把这三层**连成一张图**，
然后让"这家企业能不能授信"这个问题变成一次**有约束的路径搜索**——沿线每一跳都带着
出处（哪份文件的哪一行），终点落在**可执行的阈值**上而不是一句笼统的"存在监管要求"。

## 三、快速开始（不需要任何外部依赖）

```bash
pip install -e ".[dev]"
export PYTHONPATH=src        # Windows: set PYTHONPATH=src

# 1) 导入样例数据（12 份多模态文档）
python -X utf8 -m govfin.cli ingest --data data

# 2) 对单个主体跑一次授信决策
python -X utf8 -m govfin.cli ask 乙贸易有限公司

# 3) 按决策编号回放完整推理链
python -X utf8 -m govfin.cli replay DEC-XXXXXXXXXXXX

# 4) 跑一轮本体演化
python -X utf8 -m govfin.cli evolve --dry-run

# 5) 部署自检
python -X utf8 -m govfin.cli doctor
```

**没有 API Key 也能跑通全部流程。** 把 `GOVFIN_LLM_PROVIDER` 设为 `offline` 即走确定性
离线后端：抽取、建图、推理、决策、演化、审计全部可用，只是本体演化不再有 LLM 提案
（降级为人工仲裁队列）。这是设计内的降级路径，不是故障。

接真实模型：复制 `.env.example` 为 `.env` 并填入 DeepSeek / 任意 OpenAI 兼容端点的 Key。
`.env` 已在 `.gitignore` 中，**不会被提交**。

### 起服务

```bash
# MCP 工具服务（Nexent 通过它接入 10 个领域工具）
python -X utf8 -m govfin.mcp.server --transport streamable-http --port 8930 --ingest data

# A2A 协作服务（Agent Card 发现 + JSON-RPC 任务接口）
python -X utf8 -m govfin.a2a.server --port 8940 --ingest data
```

### 几个刻意的设计决定

**图的层数不是装饰。** Layer2（规则）必须独立成层，因为"判不判"的依据是监管条款，
而不是任何一条业务数据。`CREDIT_CHAIN` 约束强制要求路径**必须跨到规则图**——
不跨层就只是一份内部画像，不配叫决策依据。

**路径终点是「阈值」而不是「条款」。** 止步于条款只能证明"存在一条监管要求"，
取到阈值才能回答"判定边界是多少"。前者的结论不可执行。因此没有可解析阈值的条款
**不会进入结果集**，而是连同原因留在 `rejected_paths` 里等审计。

**阶段间传证据，不传摘要。** 编排日志里每一步都带 `payload` 全量返回，而不是一句
"已完成"。摘要是有损的，而决策链的每一步都可能成为事后追责的对象。

## 六、测试

```bash
python -X utf8 -m pytest -q              # 235 条，约 6 秒
python -X utf8 -m pytest -q -m stress    # 追加 13 条十万级规模压力
```

五个层次：功能回归 · 解析层模糊测试（133 条） · 混沌注入（LLM 故障 / 并发时序） ·
**对抗测试**（6 类攻击） · 导入完整性（依赖声明与静默丢失）。

对抗维度是最后加的，也是最有价值的一层。它换了个前提：**上游送进来的数据本身就是
冲着结论去的**。写它的过程中查出 7 个真实缺陷，其中一个让**样例数据集本身**就是错的
——7 条记录归属于错误的企业，而在此之前所有测试都是绿的。

容器化部署时又查出 3 个：PDF 依赖声明的是一个**从未被 import 过**的包（本地因
恰好装过真依赖而无症状，任何干净环境都解析不了 PDF）、导入时静默跳过坏文档、
Dockerfile 里两处会让容器根本起不来的写法。

详见 [`docs/测试报告.md`](docs/测试报告.md)，含每个缺陷的根因与**变异验证**结果
（回退修复 → 断言测试必须变红；首轮 9 处变异有 2 处没被抓到，因此补了针对性用例，
当前 11/11 全检出）。

## 九、诚实的边界

- **样例数据是合成的。** 结构与字段取自真实政务接口的常见形态，但主体与数值是构造的。
- **OCR 精度未做评测。** 验证的是纠正表的语义（合法字符不得被改）与"无 OCR 依赖也能
  端到端跑通"，没有对 PaddleOCR / Tesseract / VLM 的实际识别率下结论。
- **规模压力用的是合成图。** 它回答"数据量上去之后逻辑还成立吗"，不回答"真实数据分布下
  还成立吗"。
- **对抗测试覆盖的是已知攻击面**，不是穷举。
