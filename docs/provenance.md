# 决策溯源与依据漂移

> 代码：`src/govfin/reasoning/provenance.py`（写）、`src/govfin/reasoning/audit.py`（读）
> 入口：CLI `govfin replay` ／ MCP `evidence_bundle` ／ A2A 阶段「溯源」

## 一、审计和推理是同一张图的两个方向

```
推理：  事实 ──► 结论      企业 → 社保记录 → 风险指标 → 条款 → 阈值 → 判决
审计：  结论 ──► 事实      判决 → 证据束 → 逐环证据 → 原始文件与行号
```

两条路径都必须是**图上的真实边**，而不是靠 ID 前缀约定的字符串拼接。拼接看起来更省事，
但一旦有人改了 ID 规则，审计就会**静默断链**——它不报错，只是再也走不回原文，
而这时候读的人还以为自己看到了完整依据。

因此决策的每一步都作为节点与边写进 Layer3：决策节点、证据束节点、逐步快照节点，
以及 `决策依据条款` / `决策涉及实体` / `步骤引用条款` / `步骤引用实体` 四类跨层边。
这些边的合法组合由 `CROSS_LAYER_RULES` 强制校验。

## 二、冻结快照

决策作出时，被引用节点的属性会被**冻结**一份存在 Layer3（`FROZEN_KEY`）。

冻结的字段是**与结论成立与否直接相关**的那些。`_IGNORED_PROPS` 明确排除了
`id` / `ontology_version` / `create_time` / `update_time` —— 这些字段会变，
但它们的变化不影响"当初那个判断今天还成不成立"。

冻结快照要精确到这一层的理由：审计问的是"**当初**你看到的是什么"，而不是
"现在图上是什么"。如果没有冻结快照，事后有人补录了一条社保记录，审计就只能
看到补录后的值，于是要么误以为决策依据的就是新值（决策当时做对了也说不清），
要么无从判断差异（做错了也查不出）。

## 三、依据漂移检测

这是 `audit.py` 里最值得留意的一项。

决策把证据冻结在 Layer3。时间一长，Layer1 的社保记录被补录、Layer2 的条款被修订，
就会与冻结快照不一致。

**这种不一致不是错误。** 决策当时确实依据的是旧数据，用旧数据得出的结论在当时
是成立的。但它是监管问询里最常被追问的一件事：

> "这条结论放到今天还成立吗？"

因此系统必须能**主动**把它指出来，而不是等审计员逐字段比对。逐字段比对的工作量让这
件事在现实中根本不会发生——而它在合规上恰恰是必须发生的。

### 实测输出

```
✓ 未检测到依据漂移：决策所引用的证据与当前图状态一致。
```

有漂移时逐项列出 `{prop, frozen, current}`：决策时是什么、现在是什么、哪个字段。

### 两条边界

**漂移只在值真的变了时报。** 存储层用 `_same_value` 按数值比较（`5000` 与 `5000.0`
是同一个事实的两种写法，JSON 接口给 int、抽取归一给 float）。如果按字符串比，
正常重导就会堆出一串并不存在的漂移告警——而**告警机制不会因为不报而失效，
只会因为报了太多假的而失效**。

**上游合法修正也必须在漂移里看得见。** 走 `update_node_props`（"系统自己决定把字段改成
什么"）的改动同样会被漂移检测捕获。业务上确实需要数据修正，系统不拒绝；它必须做到的是
改动**留痕**。否则"这次决策当时看到的是什么"就成了不可回答的问题。

## 四、被拒路径与采纳路径同等重要

证据束里 `rejected_chains` 与 `accepted_chains` 并列保留，每条附 `reject_reason`。

只记录采纳结果，事后就无法回答"当初是不是漏看了什么"。一条被拒的链可能因为
置信度不足、可能因为跳数超限、也可能因为**终点没有可解析的阈值**——这三种原因的
业务含义完全不同，审计需要区分。

实测样例（`乙贸易有限公司`）：

```
采纳的推理链（共 7 条）：
  [企业真实性核验] 乙贸易有限公司 → GS-2026-0002   置信度 0.8834  1 跳
      ← 拥有工商登记｜direct｜工商登记信息.json｜经营范围: 日用百货销售；金属材料销售；货物进出口
  [关联方风险传导扫描] 乙贸易有限公司 → SS-202603-005 → 社保缴纳异常(2026-03)   置信度 0.6982  2 跳
      ← 缴纳社保｜direct｜社保缴纳记录.json｜缴纳状态: 断缴
      ← 触发风险信号｜derived｜社保缴纳记录.json｜缴纳状态: 断缴（判定为风险状态：断缴）
  [授信决策链生成] 社保缴纳异常(2026-03) → 经营稳定性 → 银保监发〔2024〕12号-§4.1 → 连续异常月数上限@…   置信度 0.3880  3 跳
      ← 对应指标｜derived｜银保监发〔2024〕12号-§3.2｜指标「社保缴纳异常」与条款原文共享表述「社保」
      ← 映射维度｜derived｜监管条款汇编.txt｜映射风险维度: 经营稳定性
      ← 设定阈值｜direct｜银保监发〔2024〕12号-§4.1｜连续三个月
依据条款原文：
  《银保监发〔2024〕12号-§4.1》
      授信审查应当核验借款人用工规模与营业收入的匹配性。参保人数连续三个月低于同行业
      同规模企业的，应当要求借款人补充说明并审慎核定授信额度。
✓ 未检测到依据漂移：决策所引用的证据与当前图状态一致。
```

每一跳都带 `evidence_class`（`direct` / `derived`）——审计能一眼看出哪一跳是原始
登记数据、哪一跳是规则推导。这个区分直接决定该跳在置信度模型中被打多重的折。

## 五、来源归属与冲突留痕

每个字段都要能回答"**这个值是谁给的**"。

节点的 `provenance` 含 `first_seen`（首次出现：文档 + 定位 + 模态 + 片段）与
`sources`（全部来源列表）。列表有上限（热点主体能攒出几十条），但**截断必须计数**
（`sources_dropped`）——来源列表被截短而不做声，与"从来就只有这些来源"在读的人眼里
是同一个样子，审计会拿着半份名单当成全部名单。

**多源冲突不静默覆盖。** 同一个字段有两个来源给了不同的值，系统保留**先到的**，
把两个说法连同各自的来源一起记进节点上的 `__冲突__`：

```json
{ "字段": "缴纳状态", "保留值": "欠缴", "另一来源的值": "正常",
  "来源": { "document": "伪造_社保缴纳记录.json", "locator": "record:0/缴纳状态" } }
```

保留先到的值而不是后到的，是多源数据在政务场景里唯一站得住的默认：政务数据整表
重发是日常，**一条记录编号重复出现不是异常**。若让后到的说了算，一份伪造的重发记录
就足以洗白风险信号，而且事后看不出发生过什么——节点的 `first_seen` 还指着最初那份
文件，审计追到这里会以为那句话就是原文写的。
