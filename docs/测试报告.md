# 暴力测试报告

> 对象：GovFin 决策智能体（赛题3 · 可进化决策智能体）
> 环境：Windows 11 / Python 3.13.2 / pytest 9.1.1 / SQLite(WAL)
> 结果：**248 条用例，全部通过**（235 条默认回归 + 13 条规模压力，默认跳过）

---

## 一、这一轮测试在测什么

单元测试回答的是"功能有没有写对"，而这一轮测试回答的是另一个问题：

> **这套系统在没人盯着的时候，会怎么坏。**

金融政务场景的失效不是"报错"——报错是最好的一种失效，因为它看得见。真正要命的是
那些**不报错的失效**：一份伪造的重发记录把风险信号洗白，图上不留任何痕迹；一份
字段顺序不同的材料让 A 家的处罚挂到 B 家名下，风控据此收紧额度，全程零异常；一页
营业执照的注册资本被静默丢掉，决策少了一条依据，报告照样显示"导入成功"。

因此本轮测试的全部断言都写成"**这个具体的坏结果没有发生**"，而不是"没有抛异常"——
攻击成功的标志恰恰就是不抛异常。

## 三、本轮发现并修复的缺陷

下面每一条都是先被测试逼出来、再定位到根因、修完之后**用变异验证确认测试真的能盯住它**
（见第四节）。顺序按危害从大到小。

### 3.1 风险洗白：伪造记录可以改掉图上已有的值，且不留痕迹

**症状。** 重发一条社保记录、把 `征缴状态` 从"欠缴"改成"正常"，图上那条记录的值
就真的被改掉了，`__冲突__` 里一片空白，节点的 `first_seen` 还指着最初那份文件。
审计追到这里，会以为"欠缴"这句话本来就是那份文件写的。

**根因。** `_ensure_node` 把属性当作节点的 `props` 传给 `add_node()`，而 `add_node`
执行的是 `INSERT OR REPLACE`——已存在字段**从未与现有值比较过**，冲突留痕机制被
整条绕过。更隐蔽的是加载器的 `_node_cache`：抽取器是"一个字段一个元组"，同一个
提及在一份文档里要走十几次，缓存命中才是常态；缓存短路直接 `return cached`，等于让
同一批里后到的每一个字段值都跳过来源归属与冲突留痕，直接改写节点。

**修复。** 数据属性改走 `merge_from_source(...)`（语义是"这是来源文档的说法"，不是
"系统自己决定改成什么"），缓存路径也执行合并。保留先到的值，两个说法连同各自的来源
一起记进 `__冲突__`。

### 3.2 记录归属整体错位一家（样例数据本身就已中招）

**症状。** `企业:乙贸易有限公司` 保留的是丙建材的信用代码，并拒绝了它自己正确的
那个；它自己全部五条社保记录都声称这个代码有误。逐条追下去，**7 条归属边被错挂**。

**根因。** 政务 JSON 的字段顺序由各统筹区接口自己定，而"记录编号 / 统一社会信用代码"
常常排在"企业名称"**前面**。字段一出现就落元组，这两条元组只能拿到**上一条记录**
残留的企业名，于是整表错位一家。而 `_backfill_owner_links` 只回填
`relation_candidate is None` 的元组，错挂的边早已不为 None，永不纠正。

**修复。** 引入 `_open_record` / `_flush_record` / `_emit_owned_tuple`：记录里的
归属先留空挂起，等本记录的企业名出现（或记录结束）再落定。`_backfill_owner_links`
改为**只在文档确实只讲过一家企业时**才兜底——多家企业的文档里"最后出现的那家"
不是答案，只是一个猜错的答案；**没有归属边是看得见的缺陷，错挂一条归属边是看不见的
缺陷**，两者之间没有可犹豫的余地。

修复后：14/14 条归属边正确，样例图上 0 处归并冲突、0 处节点冲突。

### 3.3 一页营业执照，除了信用代码和企业名，其余字段全部静默丢失

**症状。** `extract_license_fields()` 对样例营业执照只能返回 `统一社会信用代码` 和
`名称`；注册资本、成立日期、住所、经营范围、法定代表人、登记机关**一个都拿不到**。

**根因。** "标签 → 值"循环里用 `text[match.end():next_start]` 取值。`$` 是零宽的，
`match.end()` 落在值的**末尾**而不是开头，于是每个标签切出来都是空串，整个循环等于
从没跑过。最后能幸存的两个字段，靠的是循环之外的两条兜底正则（信用代码、企业名）——
**兜底掩盖了主路径的彻底失效**。

**修复。** 改从捕获组起点切：`match.start(2)`；跨行续接的语义保持不变。修复后
10 个字段全部正确解析。

### 3.4 OCR 纠正表把合法字符也改掉了

**症状。** OCR 边车文本写的是 `91310115MA1K3XYB02`，图上存进去的却是
`91310115MA1K3XY802`。

**根因。** 通用纠正表 `_OCR_CONFUSION` 含 `B → 8`。但 GB 32100 统一社会信用代码的
字符集是 `0-9A-HJ-NPQRTUWXY`，**B 是合法字符**（被排除的只有 I、O、S、V、Z）。
于是系统自己伪造了一个字段值，而伪造出来的代码看起来同样"合法"，会安静地写进图里、
与登记机关的原值冲突、把企业身份并到别的节点上，没有任何异常可捕获。

**修复。** 新增 `_USCC_CONFUSION`（只含 I/O/S/Z 这些**不可能合法出现**的字母）用于
所有信用代码路径；通用表保留给其它字段。**系统自己改坏一个字段值，比收到一个坏字段值
更严重**：后者至少能追到来源，前者连"谁改的"都答不上来。

### 3.5 畸形字段值在图上凭空造出一个假主体

**症状。** 一条 `企业名称: 12345` 的记录导入后，图上多了一个名字叫 `12345` 的
企业节点。

**根因。** `_coerce(v, "company")` 在正则匹配不上时 `return v`，把原文本原样收下。
节点一旦存在，关联方匹配、风险传导、授信额度都会把它当成真实主体对待，而**没有任何
环节会再回头看它像不像企业名**。

**修复。** 匹配不上返回 `None`。少一个字段是看得见的缺陷，多一个假主体是看不见的。

### 3.6 被丢掉的值在报告里查不到

**症状。** 上面那个 12345 被丢弃后，装载报告显示 `rejected_count: 0`。

**根因。** `GraphLoader.load()` 只用自己捕获到的异常填充 `rejected`，完全没有带上
`ExtractionResult.rejected`——抽取阶段判死的值在装载报告里根本不存在。

**修复。** `load()` 先把 `result.rejected` 并入报告。"全部导入成功"和"少了一个字段"
在报告上长得一模一样，没人会去查。

### 3.7 冲突表被噪声淹没

三个各自独立的问题，共同的后果是让留痕机制**因为记了太多假的而失效**
（它不会因为不记而失效，只会因为不值一看而失效）：

- **数值按字符串比**：`5000` 与 `5000.0` 是同一个事实的两种写法（JSON 接口给 int，
  抽取归一给 float），逐字比会在正常重导时堆出一串并不存在的冲突。
  新增 `_same_value()` 按数值比。
- **同一处冲突记两遍**：同一份文档里同一个字段会经两条路径各合并一次，去重后才不
  至于让一处冲突在表里出现两遍。
- **来源列表被截断而不做声**：一个被反复引用的主体能攒出几十条来源，列表有上限是对的，
  但截断必须记数（`sources_dropped`）——否则审计会拿着半份名单当成全部名单。

### 3.8 声明的 PDF 依赖与代码 import 的不是同一个包

**症状。** 容器化部署后，图比宿主机少一个节点、少 6 条边。少的是
`企业:上海某钢材贸易有限公司`——判决书里的当事人。

**根因。** `pyproject.toml` 声明 `pypdf>=4.0`，而 `pdf_parser.py` 里
`import pdfplumber`。**pypdf 从头到尾没有被任何代码 import 过；真正需要的
pdfplumber 从未被声明。** 开发机上两个包都装着（pdfplumber 是别的原因装上的），
所以本地一切正常；任何按 `pyproject.toml` 全新安装的环境——包括容器——都解析不了
任何 PDF。而缺失的 PDF 后端**不抛异常到调用方**（见 3.9），于是判决书连同它带的
那家企业一起从图上消失了：构建成功、自检全绿、决策照跑。

依赖声明写错是最难发现的一类缺陷，**因为开发机永远不会复现**。

**修复。** 把 `pypdf>=4.0` 换成 `pdfplumber>=0.11`，并加一条测试断言
"声明里必须有解析器真正 import 的那个包，且不能再挂着没人 import 的包"。

### 3.9 导入时静默跳过解析失败的文档

**症状。** 上一条之所以能一路畅通到容器里才被发现，就是因为这里：
`ingest_dir` 逐份 `try/except: continue`，跳过多少份都不说。

**根因。** "单份文档失败不该中断整批导入"这个决定本身是对的——一份坏文件不该让
当天全部材料都进不来。但**静默跳过与"这份文件本来就不存在"在报告上长得一模一样**：
读报告的人看到 `documents: 12`，会以为目录里就 12 份文件，而不是"有 12 份成功、
另有一份打不开"。

**修复。** 报告新增 `files_seen`（实际扫描到的文件数）与 `skipped`（跳过清单，
含文件名与原因）。跳过仍然不中断，但从此看得见。

### 3.10 Dockerfile 里两处会让容器根本起不来的写法

这两个都只有在**真的去构建和运行**时才会暴露——Dockerfile 此前从未被构建过。

| 写法 | 后果 | 修法 |
|---|---|---|
| `HEALTHCHECK ... CMD-SHELL curl …` | `CMD-SHELL` 是 **docker-compose 的关键字**，Dockerfile 只认 `CMD`。解析阶段直接报错，**镜像都构建不出来** | 改用 `CMD`（shell 形式，仍会展开变量） |
| `CMD ["sh", "-c", "… & wait -n"]` | Debian 的 `/bin/sh` 是 **dash**，不认 `wait -n`，容器以退出码 2 立刻结束——**镜像构建成功，容器却跑不起来** | 改用 `bash`（基础镜像自带，无需额外安装） |

第二条尤其具有讽刺意味：原注释担心的正是"健康检查失败得不明显"，而实际问题是
连健康检查都轮不到执行。

## 四、变异验证：确认测试真的盯得住

**一个不会变红的测试等于没有测试。** 一个在修复之前写、在修复之后跑绿的测试，只说明
"现在不报错"，不说明它盯住了那个缺陷——它完全可能因为别的原因通过，或者压根没走到出
问题的那条分支。唯一能证明它有效的方法，是把修复撤掉再看一遍。

第一轮 9 处变异里有 2 处**仍然通过**，暴露了两个此前没有任何测试覆盖的行为（都落在
LLM 抽取通道上），于是补了两条针对性用例。后续又为部署期的三个缺陷各补一条，
当前 **11/11 全部检出**。

这套验证已固化成脚本，可随时重跑：

```bash
PYTHONPATH=src python -X utf8 scripts/verify_mutations.py
```

|---|---|---|
| OCR 值从捕获组起点切 | `test_injected_document_cannot_launder_provenance` | ✓ 变红 |
| `_coerce` 企业名脏值返回 None | `test_a_corrupted_document_cannot_take_down_the_batch` | ✓ 变红 |

后两条（LLM 通道）是第二轮补的。它们暴露的问题值得单独说：**合并纪律有两条入口，
却只有一条被测试盯住**。规则路径的属性名受本体字段表约束、取值被 `_coerce` 归一过；
LLM 给出的属性名和取值都是自由的。若只在规则通道上做合并，后果是**顺序决定成败**——
同一个字段，在"图上还没有这家企业"时能进图，在"图上是已有企业"时被悄悄丢掉。这类
差异在图上不留任何痕迹，却让同一份材料在不同导入顺序下得到不同的图。

## 五、已知边界（没有测到的部分）

诚实列出，避免把"没测"读成"没问题"：

1. **真实 OCR 后端未做精度测试。** 只验证了纠正表的语义（合法字符不得被改、非法字符
   必须被改），没有对 PaddleOCR / Tesseract / VLM 的实际识别率下结论——那需要标注
   样本集，不是这轮的目标。管道本身在无任何 OCR 依赖的环境下可端到端跑通。
2. **规模压力用的是合成图，不是真实业务数据。** 它验证的是"数据量上去之后逻辑还成立
   吗"，不是"真实数据的分布下还成立吗"。
3. **对抗测试覆盖的是已知攻击面。** 六类攻击都是先想清楚"哪些字段最值钱、改哪个字段
   收益最大"再构造的（比如 `_RISK_STATUS` 控制的那个 `缴纳状态`），不是穷举。
4. **归属错位的触发条件是字段顺序。** 顺序把企业名排在前面的接口不会触发，所以样例
   数据在被对抗测试盯上之前，看起来完全正常——这正是它危险的地方。

## 六、这一轮测试换来的东西

比"245 条通过"更有价值的是：**样例数据集本身曾经是错的**（3.2），而在此之前所有
测试都是绿的。这说明测试的覆盖面在"自己坏掉"上很够，在"数据被人做了手脚"上远远不够。
对抗维度的价值不在于它跑出了多少用例，而在于它换了一个前提：**上游送进来的数据本身
就是冲着结论去的**。
