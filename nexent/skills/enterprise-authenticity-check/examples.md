# 企业真实性核验 — 参考示例

本文件只在默认使用方式不够用时加载。

## 示例一：信用代码精确核验

唯一键查询，最可靠的路径。

<code>
result = gov_business_lookup(subject="91310115MA1K3XYA01")
# {
#   "ok": true, "found": true,
#   "subject": {"node": "企业:甲科技有限公司", "label": "甲科技有限公司", "ntype": "企业"},
#   "records": [
#     {"记录编号": "GS-2026-0001", "注册资本": "500万元人民币",
#      "成立日期": "2018-03-12", "经营范围": "计算机软件开发；信息系统集成服务；数据处理服务；技术咨询",
#      "source_document": "工商登记信息.json", "snippet": "..."},
#     {"记录编号": "GS-2026-0002", "source_document": "营业执照_甲科技有限公司.png",
#      "snippet": "名称: 甲科技有限公司 类型: 有限责任公司（自然人投资或控股）..."}
#   ]
# }
</code>

同一个主体返回**两条记录**是正常的：登记信息来自 JSON 结构化数据，
营业执照来自图片 OCR，两者是不同模态的独立证据来源，互为印证。
不要因为记录数大于 1 就以为匹配到了多个主体——区分标准是记录编号是否相同，
而不是记录条数。

## 示例二：同名主体歧义

这是本技能最需要谨慎处理的场景。

<code>
result = gov_business_lookup(subject="乙贸易有限公司")
# {
#   "ok": false,
#   "error": "主体名匹配到多个候选",
#   "candidates": [
#     {"node": "企业:乙贸易有限公司", "统一社会信用代码": "91310115MA1K3XYB02",
#      "法定代表人": "张三", "成立日期": "2019-07-25"},
#     {"node": "企业:乙贸易有限公司", "统一社会信用代码": "91310115MA1K3XYC03",
#      "法定代表人": "李四", "成立日期": "2021-11-03"}
#   ]
# }
</code>

**处置方式**：把候选列表原样交给用户，请其确认。若用户无法确认，
结论记为"证据不足"并终止。

**不要**取第一个候选继续。同名不同主体在企业征信里是常态，
选错主体会让后面一整条决策链都挂在一个无关企业上，
而且**全程不会报错**——图照常构建、路径照常搜索、结论照常输出，
只是全错。这类错误在最终审计时才可能被发现，届时已无法追溯。

## 示例三：真实性闸门拦截

主体登记查无此记录时的完整处理。

<code>
result = gov_business_lookup(subject="上海某钢材贸易有限公司")
# {"ok": true, "found": false, "subject": {...}, "records": []}

if result["ok"] and not result["found"]:
    # 闸门未过：终止，不产生任何授信结论
    decision = {
        "verdict": "不予受理",
        "halted_at": "企业真实性核验",
        "reason": "工商登记库中查无此主体",
        "evidence": [],
    }
    # 注意：此处不应再调用 gov_social_security / gov_judicial_scan /
    # fin_financial_parser。为不存在的主体采集风险数据没有意义，
    # 且会浪费展开预算。
</code>

对应的端到端验证（`risk_decision` 内嵌闸门的行为）：

<code>
decision = risk_decision(subject="上海某钢材贸易有限公司", persist=False)
# decision["verdict"] == "不予受理"
# decision["halted_at"] == "企业真实性核验"
# len(decision["steps"]) == 1     # 终止后不产生后续步骤
</code>

`len(steps) == 1` 是这条闸门真正生效的证据。如果看到 steps 有 3 个、
结论却是"不予受理"，说明闸门是在最后才判定的，那它就没有起到拦截作用。

## 示例四：区分"查无此主体"与"查不动"

<code>
# 情形 A：数据源抖动
result = gov_business_lookup(subject="丙建材有限公司")
# {"ok": false, "error": "数据源不可达: connection timeout"}

# 正确处置：重试，失败则报"证据不足（采集失败）"
#   → {"verdict": "证据不足", "cause": "collection_failure",
#      "note": "政务数据源不可达，非查无此主体，需人工补采"}

# 错误处置：报"不予受理"或"未发现风险"
#   → 前者把可修复的技术故障说成了业务事实
#   → 后者把"不知道"伪装成了"没问题"
</code>

这两种错误处置的代价不对称：把"查不动"说成"不存在"，会让一个正常企业被拒贷；
说成"无风险"，会让一个未核验的主体进入授信流程。后者是信贷场景里最危险的错误。
