# 企业真实性核验

判断一个授信主体**是否真实存在**，以及支撑这个判断的**证据来自哪里**。

这是整个授信流程的第一道闸门。它回答的不是"这家企业好不好"，而是更靠前的问题：
"这家企业是不是真的。"没有通过这一关的主体，后面所有风险分析都是在给一个
可能不存在的对象做画像。

## 可用方法

`gov_business_lookup`

## 方法参数

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| subject | string | 是 | - | 企业名称或统一社会信用代码 |

**优先传统一社会信用代码。** 它是唯一键，而企业名称可能撞上同名主体
（尤其是"某某科技有限公司"这类高频名）。用户同时给出两者时，用信用代码查，
再用名称交叉印证。

## 使用方式

<code>
result = gov_business_lookup(subject="91310115MA1K3XYA01")
if not result["ok"]:
    # 工具没执行成功 ≠ 查无此主体。见下方"错误处理"第一行。
    raise RuntimeError(result.get("error", "查询失败"))

if not result["found"]:
    conclusion = "不予受理"          # 登记库中确实没有这个主体
else:
    evidence = result["records"]      # 每条自带 source_document 与 snippet
    bundle = evidence_bundle(subject="91310115MA1K3XYA01")
</code>

## 返回值

```
{
  "ok": true,            // 工具本身是否执行成功
  "found": true,         // 是否查到登记记录
  "subject": { "node": ..., "label": ..., "ntype": "企业" },
  "records": [ { ..., "source_document": ..., "snippet": ... } ]
}
```

**`ok` 和 `found` 必须分开理解**，这两者对应完全不同的处置方式：

| 情况 | 含义 | 该怎么办 |
|---|---|---|
| `ok=true, found=true` | 查到了，主体真实 | 继续，进入风险采集 |
| `ok=true, found=false` | 查询成功，但**登记库中确实没有这个主体** | **终止流程**，结论"不予受理" |
| `ok=false` | 工具**执行失败**，查询没做成 | 重试或降级，**绝不能当成"查无此主体"** |

把 `ok=false` 当成 `found=false` 是本技能最容易犯的错误。两者在业务上恰好相反：
一个是"确认不存在"，一个是"暂时不知道"。

## 证据口径

本技能只采纳 `evidence_class = direct` 的路径——即来自政务原始登记数据、
未经任何推导的证据。

派生证据（规则推导）和 LLM 证据（模型生成）**一律不计入**真实性判定。
理由是真实性是个二值事实，它不应该被概率推理修饰：企业要么在登记库里，
要么不在。如果允许 LLM 生成的描述参与"这家企业存在"的判断，
整个闸门就失去意义了。

**采纳阈值 0.8**，显著高于其他约束。这不是随意设的高线：1–2 跳的直接登记证据
天然能拿到 0.85 以上；把阈值定在这里，实际含义是"当政务数据采集不完整时，
宁可拒绝下结论，也不要基于残缺证据给出通过"。在授信场景里，
把不存在的主体误判为存在，代价远高于把存在的主体退回补件。

## 错误处理

| 错误 | 原因 | 解决方案 |
|------|------|----------|
| `ok=false`，`error` 为数据源不可达 | 政务数据源暂时不可用 | 指数退避重试 2 次；仍失败则结论"证据不足"，并**明确标注这是采集失败而非查无此主体**，转人工补采 |
| `ok=false` 且 `graph_stats` 显示节点数为 0 | 图谱未加载 | 先确认图谱已导入（`govfin doctor`）再重试 |
| `ok=false`，返回多个候选 | 主体名模糊，匹配到多个同名实体 | **不要替用户猜**。把候选原样呈现（每个带信用代码以便区分），请用户确认。若无法确认，结论记为"证据不足" |
| `ok=true, found=false` | 登记库中确实没有这个主体 | 立即终止，输出"不予受理"。**不要**用社保/司法/财务数据反推主体存在性——这些数据源在采集链路上都晚于工商登记，出现"工商无登记、社保有缴纳"只可能是数据质量问题，应当上报而非据此判定主体存在 |
| `found=true` 但采纳路径为空 | 登记记录存在，但证据链置信度未达 0.8 | 调 `evidence_bundle` 取回被拒路径及理由，转人工复核。**不要下调阈值来"让它通过"** |
| 返回 `truncated=true` | 展开预算耗尽，结果可能不完整 | 收紧约束重试（减少 `max_hops`），不要直接采信截断结果 |

## 输出契约

核验结论必须包含三样东西，缺一不可：

1. **结论**：通过 / 不通过 / 无法判定
2. **依据**：命中的登记记录，逐条附 `source_document` 与 `snippet`
3. **口径声明**：本次核验只采纳 `direct` 类证据，采纳阈值 0.8

第 3 项不是形式主义。监管问询时第一个问题永远是"你这个结论是怎么来的"，
口径声明让这个答案不需要重新推导一遍。

## 与下游的契约

本技能的输出是 `counterparty-risk-contagion-scan` 的**前置条件**：

- 结论"通过" → 继续，把 `subject.node` 传给下游
- 结论"不予受理" → 终止，不再调用任何后续技能
- 结论"证据不足" → 转人工，人工给出明确结论前不继续

`risk_decision` 内部也实现了同一道闸门（"真实性闸门"阶段）。
两者判定逻辑一致，区别是：本技能是**显式的、可单独调用的、面向用户的**；
`risk_decision` 里那道是**内嵌的、不可跳过的**。单独调用本技能是为了在流程
早期就拿到结论，避免为注定失败的主体做无用展开。
