# 授信决策链生成 — 参考示例

本文件只在默认使用方式不够用时加载。

## 示例一：完整决策（触发阈值）

<code>
decision = risk_decision(subject="甲科技有限公司")
# {
#   "ok": true,
#   "subject": {"node": "企业:甲科技有限公司", "label": "甲科技有限公司"},
#   "verdict": "审慎核定",
#   "confidence": 0.5799,
#   "judgements": [{
#     "threshold_name": "连续异常月数上限",
#     "threshold_value": 3.0,
#     "direction": "上限",
#     "observed_value": 3.0,
#     "observed_basis": "同维度风险指标出现 3 次",
#     "triggered": true,
#     "clause_node": "授信指引条款:银保监发〔2024〕12号-§4.1",
#     "clause_label": "银保监发〔2024〕12号-§4.1",
#     "indicator_nodes": ["风险指标:290dc6e1...", "风险指标:5dd5a4c7...", "风险指标:bd23c705..."]
#   }],
#   "steps": [
#     {"序号": 1, "操作": "企业真实性核验",     "采纳路径": 2,  "中间结论": "命中 2 条政务登记证据"},
#     {"序号": 2, "操作": "关联方风险传导扫描", "采纳路径": 12, "中间结论": "命中 3 个风险指标"},
#     {"序号": 3, "操作": "授信决策链生成",     "采纳路径": 1,  "中间结论": "形成 1 条阈值判定依据"}
#   ],
#   "provenance": {"decision_id": "DEC-322EEB4768D5", "accepted_paths": 17}
# }
</code>

**注意 `triggered: true` 的判定依据**：观测值 3、阈值 3，判定式是 `>=` 而非 `>`。
监管条款写"连续三个月"时，第三个月已经构成触发条件，不需要第四个月。
这个细节在边界情形下直接决定结论。

**注意阶段 2 和阶段 3 的路径数差异**：12 条传导路径收敛成 1 条阈值判定。
这是正常的——12 条是风险信号的不同走法，1 条是去重后的判定依据。
如果看到阶段 3 的路径数也是 12，说明去重没生效，同一份证据被当成了 12 份。

## 示例二：依据链的完整性

<code>
dec_id = risk_decision(subject="甲科技有限公司")["provenance"]["decision_id"]
bundle = evidence_bundle(decision_id=dec_id)
# {
#   "clauses": [{
#     "label": "银保监发〔2024〕12号-§4.1",
#     "text": "授信审查应当核验借款人用工规模与营业收入的匹配性。参保人数连续三个月
#              低于同行业同规模企业合理区间的，应当要求借款人补充说明并审慎核定授信额度。"
#   }],
#   "accepted_chains": [...],
#   "rejected_chains": [...],
#   "drift": []
# }
</code>

条款原文必须出现在依据链里。没有原文，业务方无法判断这条判定依据是否真的适用——
条文措辞的细微差别（"应当"vs"可以"、"审慎核定"vs"不予受理"）
直接决定同一组事实下的正确结论。

## 示例三：依据漂移检测

决策作出后，图上的原始数据发生了变化。

<code>
drift = evidence_bundle(decision_id=dec_id)["drift"]
# [{"node": "社保缴纳记录:SS-202602-004", "prop": "缴纳状态",
#   "frozen": "欠缴", "current": "正常", "path": "..."}]
</code>

**处置原则**：`drift` 非空不代表决策有错——它表示该结论是在旧数据下作出的，
需要在今日数据下重新评估。列出 drift 项，让业务方决定是否重跑。

不要静默忽略（等于让决策悄悄过期），也不要仅因 drift 就推翻原决策
（数据修正未必改变结论，重跑一次才知道）。

注意同一变化只报告一次。一条传导链会经过多个节点，如果按路径逐条报告，
同一个字段变化会出现 7 次——噪声会淹没真正的信号。

## 示例四：反向查询——某条款被废止时

<code>
# 监管文件废止后，找出所有引用了它的历史决策
affected = trail.decisions_referencing("授信指引条款:银保监发〔2024〕12号-§4.1")
for d in affected:
    print(d["decision_id"], d["subject"], d["verdict"], d["timestamp"])
</code>

这是监管问询的高频问题。条款被废止或修订时，需要立刻知道哪些存量决策
建立在它的基础上，以及各自是什么结论——这决定了补救范围。

同一能力也可以回答"这条规矩我们执行得怎么样"：查出所有引用了某条款的决策，
看结论分布，就能发现执行口径是否一致。

## 示例五：规则覆盖不足的识别

结论是"建议通过"，但需要确认这是"确实没风险"还是"没找到适用条款"。

<code>
decision = risk_decision(subject="戊物流有限公司")
stage3 = next(s for s in decision["steps"] if s["序号"] == 3)

if decision["verdict"] == "建议通过" and stage3["采纳路径"] == 0:
    # 阶段 3 一条路径都没有 —— 可疑：不是没风险，而是没找到条款
    status = ontology_status()
    # {
    #   "unk_pool": {"候选数": 47, "高频未演化": ["应收账款周转天数", "关联担保余额", ...]},
    #   "pending_proposals": 3
    # }
    note = "规则覆盖不足：UNK 储备池中 47 个概念未演化，本次'未触碰阈值'结论不可靠"
</code>

`采纳路径 = 0` 加 `建议通过` 这个组合，是本技能最需要警惕的假阴性。
它看起来是个干净的通过结论，实际什么都没验证。

对照情形：如果阶段 3 有采纳路径但都没触发阈值，那是**真的**没触碰边界，
结论可信。

## 示例六：本体演化的介入时机

<code>
status = ontology_status()
if status["unk_pool"]["候选数"] > status["unk_pool"]["已演化数"] * 2:
    # 储备池远大于已演化量 —— 本体跟不上数据
    # 触发一轮演化（符号对齐优先，LLM 只补语义细节）
    result = ontology_evolve(commit=False)   # 先 dry-run 看提案
    # {
    #   "proposals": [{"kind": "alias", "from": "应收账款周转天数", "to": "应收账款周转率",
    #                  "confidence": 0.93, "verdict": "auto_accept"}],
    #   "rejected": [{"kind": "new_class", "name": "供应链金融敞口",
    #                 "reason": "一致性验证未通过：引入 3 处新增违规"}]
    # }
</code>

**符号对齐优先于新类创建**。"应收账款周转天数"与"应收账款周转率"是同一概念
的不同说法，学成别名即可，不该新建一个类。LLM 只能补语义细节，
不能决定是否需要演化——这个判定由符号对齐给出。

未通过一致性验证的提案退回人工仲裁，而不是强行提交。
演化引入的错误会污染图上所有后续推理，代价远高于多等一次人工确认。
